Documento de Requisitos do Sistema (DRS)

Projeto: oMenu - Cardápio Digital Acessível

Este documento define os requisitos funcionais e não funcionais do sistema oMenu, estabelecendo as bases técnicas e de acessibilidade para o desenvolvimento da plataforma de cardápio digital inclusivo.

Detalhe Descrição
Versão 1.0
Data 11 de Outubro de 2025
Metodologia Adotada SDLC (Ciclo de Vida) e DevOps (Desenvolvimento)
Tecnologias-Chave PostgreSQL, Python/Django Rest Framework, React, Redis (Cache)

1. Requisitos Funcionais (RF)

Os Requisitos Funcionais (RF) definem o que o sistema deve fazer para entregar valor aos seus usuários.

RF.01: Módulo do Cardápio (Interface do Usuário Final)

ID Requisito Funcional Prioridade
RF.01.01 O sistema deve exibir o cardápio em duas versões: Modo Acessibilidade (PCD) e Modo Padrão (Geral). Crítica
RF.01.02 O cardápio deve permitir a visualização de fotos realistas e a descrição completa de cada item. Alta
RF.01.03 O usuário deve conseguir adicionar, remover e ajustar a quantidade de itens no seu carrinho (cesta de pedidos). Crítica
RF.01.04 O sistema deve permitir a seleção de opção de pagamento (e.g., Pagar na Mesa, Pagar no Caixa, ou métodos digitais integrados) antes do envio do pedido. Alta
RF.01.05 O usuário deve conseguir enviar o pedido para a Cozinha/Copa em tempo real, com confirmação visual/auditiva. Crítica
RF.01.06 O sistema deve permitir que o usuário acompanhe o status do pedido em tempo real (Enviado, Em Preparo, Pronto, Entregue). Alta
RF.01.07 O sistema deve oferecer a opção de Chamar Garçom (por meio de sinalização para o Painel Operacional). Média
RF.01.08 O cardápio deve ser acessível por QR Code e/ou link via WhatsApp. Alta

RF.02: Módulo Operacional (Salão, Cozinha e Copa)

ID Requisito Funcional Prioridade
RF.02.01 O sistema deve ter um Painel de Controle do Salão que exiba a visualização em *layout* das mesas (Mapa de Mesas). Crítica
RF.02.02 O Painel de Mesas deve exibir o status em tempo real de cada mesa (Livre, Ocupada, Aguardando Pedido, Precisa de Ajuda). Crítica
RF.02.03 O sistema deve gerar telas de *display* específicas para Cozinha e Copa que exibam os novos pedidos em tempo real. Crítica
RF.02.04 A equipe da Cozinha/Copa deve conseguir alterar o status do pedido (e.g., de 'Em Preparo' para 'Pronto' ou 'Entregue'). Crítica
RF.02.05 O sistema deve permitir que o administrador do restaurante insira e gerencie todo o *layout* do cardápio (CRUD de Categorias, Produtos, Preços, Descrições e Fotos). Crítica

RF.03: Módulo de Autenticação e Gestão B2B (SaaS)

ID Requisito Funcional Prioridade
RF.03.01 O sistema deve gerenciar o acesso por múltiplos perfis (Gerente, Garçom, Cozinha, Administrador do Sistema). Crítica
RF.03.02 O módulo administrativo deve permitir a gestão de planos de assinatura SaaS e faturamento do cliente B2B. Alta
RF.03.03 O sistema deve gerar relatórios básicos de vendas, pedidos e itens mais consumidos. Média

2. Requisitos Não Funcionais (RNF)

Os Requisitos Não Funcionais definem as qualidades, restrições e o ambiente técnico do sistema, com foco especial na qualidade de Acessibilidade.

RNF.01: Acessibilidade e Usabilidade (Qualidade Crítica do Projeto)

ID Requisito Não Funcional Descrição
RNF.01.01 Leitura por Voz Integrada O sistema deve ter um recurso de leitura por voz nativa do cardápio e ser compatível com *screen readers* do sistema operacional.
RNF.01.02 Compatibilidade com Leitores de Tela O *frontend* (React) deve ser 100% compatível (A11y/ARIA) com tecnologias assistivas como TalkBack e VoiceOver.
RNF.01.03 Modo Alto Contraste O sistema deve oferecer a opção de Modo Alto Contraste para clientes com baixa visão.
RNF.01.04 Modo Daltonismo O sistema deve oferecer um Modo Otimizado para Daltonismo, ajustando as paletas de cores.
RNF.01.05 Ajuste de Fonte Total O usuário deve ter a opção de aumentar/diminuir o tamanho da fonte, com suporte para fontes de até 24px, sem quebrar o layout (Design Universal).
RNF.01.06 Navegação Simples A navegação deve ser objetiva e intuitiva, com filtros e pesquisa por texto.
RNF.01.07 Orientação e Wayfinding O sistema deve ter uma funcionalidade para ajudar o usuário a se orientar no salão e identificar uma mesa livre (conectado ao RF.02.01).

RNF.02: Desempenho e Confiabilidade

ID Requisito Não Funcional Descrição
RNF.02.01 Latência de Pedidos O tempo de transmissão do pedido do cliente para a Cozinha/Copa não deve exceder 2 segundos.
RNF.02.02 Confiabilidade (*Uptime*) O sistema deve garantir uma disponibilidade mínima de 99.8%.
RNF.02.03 Escalabilidade A arquitetura deve suportar picos de uso (ex: fins de semana), com capacidade de integrar Redis para *caching*.
RNF.02.04 Tempo de Resposta do Front O tempo de carregamento e resposta da interface do cardápio (React) deve ser inferior a 1.5 segundos.

RNF.03: Restrições e Ambiente Técnico (RNF.TEC)

ID Requisito Não Funcional Descrição
RNF.TEC.01 Banco de Dados O sistema deve utilizar o PostgreSQL para persistência de dados.
RNF.TEC.02 Backend/API O *backend* deve ser desenvolvido em Python utilizando o Django Rest Framework.
RNF.TEC.03 Frontend/Interface O *frontend* deve ser desenvolvido em React.
RNF.TEC.04 Arquitetura de Desenvolvimento O projeto deve aderir à metodologia DevOps, com Integração Contínua (CI) e Testes Contínuos.
RNF.TEC.05 Cache O sistema deve prever a integração do Redis como camada de caching e gerenciamento de sessões, se necessário para otimização.
